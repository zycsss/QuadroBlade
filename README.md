## Introduction

**LSY Autonomous Drone Racing** is a course project designed to help you develop and evaluate autonomous drone racing algorithms — both in simulation and on real Crazyflie hardware.  
Whether you’re new to drones or an experienced developer, this project provides a structured and practical way to explore high-speed autonomy, control, and perception in dynamic environments.

To get started, visit our [official documentation](https://learnsyslab.github.io/lsy_drone_racing/getting_started/general/).

## Dependencies

This project builds upon [**crazyflow**](https://github.com/learnsyslab/crazyflow), an open-source, high-speed, high-fidelity drone simulator with strong sim-to-real performance developed by the [Learning Systems Lab (LSY)](https://www.ce.cit.tum.de/lsy/home/) at TUM.

## Difficulty Levels

Each task setup — from track design to dynamics configuration — is defined by a TOML file (e.g., [`level0.toml`](config/level0.toml)).  
The configuration files specify progressive difficulty levels from easy (0) to hard (3):

|      Evaluation Scenario      | Rand. Inertial Properties | Randomized Obstacles, Gates | Random Tracks |             Notes              |
| :---------------------------: | :-----------------------: | :-------------------------: | :-----------: | :----------------------------: |
| [Level 0](config/level0.toml) |           *No*            |            *No*             |     *No*      |       Perfect knowledge        |
| [Level 1](config/level1.toml) |          **Yes**          |            *No*             |     *No*      |        Adaptive control        |
| [Level 2](config/level2.toml) |          **Yes**          |           **Yes**           |     *No*      |          Re-planning           |
| [Level 3](config/level3.toml) |          **Yes**          |           **Yes**           |    **Yes**    |        Online planning         |
|         **sim2real**          |     **Real hardware**     |           **Yes**           |    **Yes**    | Simulation-to-reality transfer |

Throughout the semester, teams in the course will compete to achieve the fastest autonomous race completion times.

## MPCC Controller (Levels 0, 1 and 2)

`config/level0.toml`, `level1.toml` and `level2.toml` use a Model Predictive Contouring Control
(MPCC) controller (`lsy_drone_racing/control/my_controller.py`) that tracks an obstacle-avoiding path
generated by `lsy_drone_racing/control/path_planning.py`. The formulation follows [Model Predictive
Contouring Control for Time-Optimal Quadrotor Flight](https://rpg.ifi.uzh.ch/docs/TRO22_Romero.pdf)
(Romero et al., IEEE T-RO 2022): the stage cost penalizes the lag and contour error with respect to
the path and rewards progress along it, with the contouring weight peaking at the gates.

The optimal control problem is generated and solved with [acados](https://github.com/acados/acados)
(`SQP_RTI`, `N=40`, 50 Hz). The solver is compiled once and cached in `c_generated_code/`; changing
any weight or horizon regenerates it automatically.

The controller commands attitude and collective thrust (`env.control_mode = "attitude"`). Three
mechanisms keep the success rate high, in preference to lap time: the reference path speed is capped
by the lateral acceleration the path curvature allows, so the drone slows down where the path bends
and passes the gates accurately; the drone's mass is estimated online from the integrated vertical
force balance and used to rescale the commanded thrust, which is what makes level 1 (randomized mass
and inertia) reliable; and a change of the observed gate or obstacle pose triggers a re-plan of the
path, which is what makes level 2 (randomized, only locally revealed poses) work. For randomized
tracks the planner also forces a straight passage through every gate and keeps the path out of the
solid gate frames it is not passing through.

**Obstacle routing.** The side on which the path passes a pole is decided by a two dimensional A*
search over a rasterized top view of the track
([`lsy_drone_racing/control/astar.py`](lsy_drone_racing/control/astar.py)) instead of by the local
push-out heuristic alone. Only the chords *between* two consecutive gate passages are rerouted; the
passages themselves stay on the gate normal, because a path that leaves the normal inside the opening
clips the frame. The search is two dimensional for a reason: the obstacles are vertical cylinders
spanning the whole flight altitude band and the gate altitudes are prescribed by the gate order, so
there is nothing to discover in `z`. It costs about 2 ms per plan at 10 cm cells.

The required clearance between the path and a pole centre is `PathConfig.safety_distance`, 0.15 m,
measured centre to centre — about 4.5 cm of air around a 0.09 m drone and a 0.015 m pole. Both
planner layers use that one number. When the search does run it blocks `safety_distance *
push_scale` = 0.21 m around each pole, for the same reason the heuristic detour waypoints are placed
farther out: the smoothing pass cuts inside a corner, so a route that only just satisfies the
clearance ends up below it. A chord that already keeps the plain 0.15 m is left alone, though, and
that distinction matters: with the overshot margin used as the trigger, a leg whose straight line
passed 0.163 m from a pole was rerouted for the sake of 13 mm, which put a visible kink where the
detour rejoined the gate block. `[controller]` in a race config may override `use_astar`,
`astar_resolution` and `safety_distance` without code changes.

Measured on level 2, seeds 0-3 (`debug_run.py --n_runs 4`):

| route | finished | mean time | path | min clearance |
| --- | --- | --- | --- | --- |
| heuristic push-out | 4/4 | 12.62 s | 13.48 m | 0.150 m |
| A* route | 4/4 | 12.63 s | 13.52 m | 0.150 m |

That is a dead heat, and worth stating plainly: once the unnecessary detours are gone, the heuristic
push-out already reaches the required clearance everywhere on this track, so the search has nothing
left to fix here and the two differ by 4 cm of path and 10 ms. The route search is the more general
method — it also decides the side of a pole rather than inheriting it from where a waypoint landed —
and it is never worse in these measurements, but it is not buying lap time on level 2. Both routes
sit at exactly 0.150 m at their tightest point, i.e. on the requirement with no margin.

**Gate passages and corners.** `gate_straight_length` is the length over which the path is forced
straight through a gate. It is the parameter that controls how tight the corners next to a gate get:
halving it from 0.55 m to 0.275 m cuts the peak curvature from 14.7 1/m to 5.9 1/m (heuristic route
14.9 to 6.2 1/m), so the sharpest corner goes from a 6.9 cm to a 16.9 cm radius, and the curvature
speed limit there (`v <= sqrt(a_lat_max / curvature)` with `a_lat_max` 4.0) rises from 0.52 m/s to
0.82 m/s. The lap time drops from 12.68 s to 12.63 s at unchanged clearance.

`approach_distance`, the +-0.6 m in/out waypoints along the gate normal, is *not* the lever for this:
halving it to 0.3 m shortens the path by 1.2 m but pushes the 95th-percentile curvature from 3.5 to
4.6 1/m, i.e. it makes the corners tighter rather than looser. Shortening `gate_straight_blend` from
0.25 m to 0.10 m is worse still for the sharpest corner (5.9 to 10.1 1/m), so it stays at 0.25 m.
Halving *both* the straight passage and `approach_distance` is the best configuration measured
statically — 12.18 m path and a 95th-percentile curvature of 3.07 1/m — but it gives up peak
clearance (0.217 m to 0.162 m), so it is the next thing to try in closed loop rather than the default.

```bash
# headless flight with a per-episode verdict and the planned path + flown trajectory
python scripts/debug_run.py --config level1.toml --controller my_controller.py

# several episodes with a success rate and mean time
python scripts/debug_run.py --config level1.toml --controller my_controller.py --n_runs 10

# rendered flight (the configs enable the GUI by default)
python scripts/sim.py --config level0.toml

# what the planner decided, without flying (the same figure debug_run.py writes per episode)
python scripts/plot_path.py --config level2.toml
```

`python` has to resolve to the repository's pixi environment; from a plain shell use
`pixi run python scripts/debug_run.py ...`. For a config that still declares
`control_mode = "state"`, pass `--control_mode attitude` to `debug_run.py`.

Results on this machine, 8 episodes each: level 0 and level 1 finish 8/8 at 8.90 s mean, level 2
finishes 6/8 at 11.7 s mean. Without the re-planning hook level 2 only finishes 2/8, so the re-plan
is what carries that level. Tunables live in `MPCCConfig` (weights, horizon, speed limits, mass
adaptation), its `a_lat_max` (the success/speed trade-off) and `PathConfig` (gate approach
distances, obstacle clearance, smoothing, gate passage shaping). The acados code generation needs the
repository's acados setup (`tools/setup_acados.bat` on Windows, `tools/setup_acados.sh` elsewhere).
