# Autonomous Drone Racing — level 2 entry

A Model Predictive Contouring Control (MPCC) racing controller for the
[LSY Autonomous Drone Racing](https://learnsyslab.github.io/lsy_drone_racing/) challenge, built on
[Crazyflow](https://github.com/learnsyslab/crazyflow). The drone tracks a re-planned, obstacle-free
B-spline trajectory through the gates, and re-plans whenever a gate or pole is revealed at a new pose.

| scenario | success | mean lap |
| --- | --- | --- |
| level 0 (perfect knowledge) | 2/2 | 8.43 s |
| level 1 (randomized mass) | 2/2 | 8.43 s |
| **level 2 (randomized poses, revealed in flight)** | **35/40** | **8.37 s** |

Level 2 is the competition setting and the only one where re-planning matters. All figures are 40
seeds on CPU; the measurement protocol and the failure analysis behind them are in
[the planning record](docs/planning/incremental_replanning.md). Each level is a TOML file in
`config/`: level 0 is perfect knowledge, level 1 randomizes mass and inertia, level 2 also randomizes
gate and pole poses and reveals them in flight.

## Running it

```bash
pixi run python scripts/debug_run.py --config level2.toml --n_runs 20   # success rate + time
pixi run python scripts/sim.py --config level2.toml                     # rendered flight
pixi run ruff check lsy_drone_racing/ && pixi run -e tests pytest       # lint + tests
```

The MPCC solver is generated by acados and cached in `c_generated_code/`. The first run after a change
to an OCP weight, the horizon or the model takes a minute to compile it; every later run reuses it.
`config/*.toml` are byte-identical to the official ones on purpose — the competition checks them, so
all tuning lives in code defaults and in the `[controller]` section of a *scratch* config.

## Pipeline

Two loops. The fast one runs at 50 Hz and never plans; the slow one runs whenever the observation
contradicts the model.

```
   observe --> pose changed? --no--> MPCC --> attitude + thrust
                   |                  ^
                  yes                 |
                   v                  |
                planner --------------+   (~16 ms, MPCC is 0.9 ms)
```

## The planner

A re-plan starts on the path it replaces and leaves it along the drone's measured velocity, so the
drone is never asked to turn around. Each stage removes one specific failure that was measured:

```
   gates in passing order + poles
     +-> _insert_detours .... a straight row of waypoints through each opening
         +-> _connect_blocks  2D A* on 5 cm cells, per chord: which side of a pole
             +-> _smooth_path  Laplacian sweeps, so turns become arcs
                 +-> _avoid_gate_frames  stay out of every gate's solid frame
                     +-> _to_bspline_path  pin Q0..Q2 to (p, v, a) of the drone
                         +-> relax  straighten what is too tight, clear the poles
                             +-> BsplinePath: pos / tangent / curvature / closest
```

The last two stages are what the speed comes from: the B-spline gives the plan a time parameterisation,
so `|v|` and `|a|` are bounded on *control points* and therefore on the whole curve (`retime`), and the
relaxation rounds the curvature no speed can fly — the plan used to contain a 0.19 m hairpin around a
pole, which needs 12 m/s^2 at 1.5 m/s and was simply cut by the controller.

## The controller

MPCC over a 40-step horizon at 50 Hz (acados, `SQP_RTI`), following
[Romero et al., T-RO 2022](https://rpg.ifi.uzh.ch/docs/TRO22_Romero.pdf):

```
   cost      q_contour x (contour error)^2        ← peaks at gates and poles
           + q_lag     x (lag error)^2
           - mu_speed  x progress along the path ← the racing objective
           + r_vtheta  x (path speed)^2
           + attitude / rate penalties

   model     identified first-order attitude lag + thrust
   command   attitude + collective thrust

   speed law  v_ref = min( sqrt(a_lat_max / curvature),   ← corners
                           mu_speed / (2 (w_gate · proximity + r_vtheta)),
                           v_actual + v_lead )            ← no jumps
```

Two mechanisms carry the success rate: the mass is estimated online and rescales the commanded thrust
(level 1), and the contouring weight is scaled up near gates so the drone gives up speed there and
crosses the opening centrally (level 2).

## The re-planning loop

Level 2 reveals each gate and pole only when it comes into sensor range, so every reveal invalidates
the path the drone is following:

```
  t0  drone flies the plan                 plan built with the nominal pose
  t1  a gate enters range, pose corrected  -> re-plan triggered
  t2  seed = (anchor on the old path, drone velocity, acceleration)
       the plan starts there and leaves along the velocity, not the old tangent
  t3  the drone pays for the correction    -> post-replan slowdown, 0.5x for 0.8 s
  t4  the pass is crossed, the plan is re-seeded on the next gate
```

The slowdown is not a safety fudge: it is the 1.5 s of lap time that buys 13 of the 40 seeds. Removing
it takes the mean lap from 8.37 s to 6.89 s and the success rate from 35/40 to 22/40.

## Where the numbers come from

Every claim above is reproducible from the scripts in `scripts/` and the record in `docs/`, which lists
each failure, the mechanism behind it, and what was tried:

| document | content |
| --- | --- |
| [incremental_replanning.md](docs/planning/incremental_replanning.md) | re-plan design, failure classes, B-spline, speed sweep |
| [fast_replanning.md](docs/planning/fast_replanning.md) | the acados formulation, and how to add a term |
| [characterisation.md](docs/control/characterisation.md) | what the drone can do: lines, circles, corners, steps |

The failures that remain are one class: margins. The plan keeps 0.17–0.19 m from a pole whose contact
radius is 0.114 m, and the drone's transient after a reveal reaches 0.10–0.23 m, so the margin is spent
by the correction itself. That is why the reference-speed knobs do not make the drone faster — raising
`mu_speed` was measured to change nothing and raising `a_lat_max` to be 0.5 s *slower* — and why the
remaining work is about making the correction smaller, not the path smoother.
